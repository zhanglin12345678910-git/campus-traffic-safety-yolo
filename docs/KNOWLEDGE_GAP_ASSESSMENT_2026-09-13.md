### 2.3 三条发现

**发现 1：逆行「写了但用不上」，是三处断裂的叠加。**

| 层 | 事实 | 证据位置 |
|---|---|---|
| 检索层 | 逆行章节 0/5 进 top5 | 上表 |
| 检测层 | **「逆行」不是模型的输出类别**（TT100K 45 类、COCO 6 类都没有它）；**图片路径完全没有逆行判定**（单帧静态图物理上判不出行驶方向）。只有**视频**路径能判，且要求调用方手传 `allowed_direction` | `backend/app/tools/video_analytics.py:173` `_is_wrong_way()`、`:43` `analyze(..., allowed_direction)` |
| 闭环层 | `POST /video-analytics` 的结果**不入库** → 不触发 RAG → 逆行知识永远不会被激活 | `backend/app/api/router.py:487` |

**根因在检测层**：模型产不出「逆行」这个词 → 查询词里永远不会有「逆行」
→ 无论文档怎么写检索关键词行，都只能靠区域名与类别代号去蹭分数，而实测蹭不上。

**发现 2：检索存在「通用词块霸榜」现象（首次量化）。**

《校园交通安全管理实践》里「6. 安全教育宣传渠道」那一块，堆叠了

与查询主题基本无关。这是 **哈希嵌入 + 长块堆词** 的结构性问题：
通用词越多，与任何查询的 n-gram 重合面越大。

**发现 3：有接口、无知识。**

系统已接高德天气（`GET /api/v1/maps/weather`，前端顶栏在显示），
但知识库里「雨天 / 湿滑 / 雾」**命中 0 份文档** ——
天气数据拿到了，却没有任何判定规则告诉模型「雨天该看什么、该定什么级」。

### 决策 A：知识库的业务边界划到哪？

**现状**：库里是「校园交通 + 消防生命通道 + 治安保卫条例（法规层）」。
`校园安全` 这个更大的范畴里，治安事件处置、门禁与外来人员、反诈、食品安全、实验室安全**都没有覆盖**。

**选项**：

- **A1（建议）**：维持现状，**只做「视觉可验证」的隐患**。
  理由：巡检系统的证据来源是图片/视频。反诈、食品安全这类主题**检不出证据**，
  补进库只会变成第二个「逆行」——文档躺在库里、报告引不到、还挤占召回席位。
- **A2**：扩到治安/门禁类。需要先回答一个问题：**门禁状态、外来人员从哪里获得证据？**
  如果答案是「没有」，那就不该补。
- **A3**：扩但只补「有法规依据 + 有视觉证据」的交叉部分（如占用消防通道、车辆乱停已覆盖）。

### 决策 B：逆行闭环要不要打通？

**事实**：逆行判定**已经实现**，在视频路径（ByteTrack 轨迹方向 vs `allowed_direction`），
但**结果不入库**，所以：视频判出的逆行 → 不进任务库 → 不触发 RAG → 报告里没有逆行依据。

**选项**：

- **B1**：保持现状，**在文档里如实标注「逆行判定仅视频可用、且不入库」**，不打通。
  代价：这个能力停留在演示级。
- **B2**：打通闭环 —— 让视频逆行事件落库并走 RAG。
  这是**开发工作量，不是知识库工作量**。需要评估：数据模型要不要加字段、前端要不要展示、
  视频任务的 `status` 与复核流怎么走。
- **B3**：评估用 **VLM** 补 —— 见 `docs/VLM_INTEGRATION_PROPOSAL.md`。
  注意：**逆行本质是时序行为，单帧图像判不出行驶方向**，
  VLM 单图也解决不了逆行；但 VLM 对**乱停车**（决策外的另一场景）确实能发挥作用。
  建议把这条单独评估，不要和逆行混为一谈。

### 决策 C：检索技术路线怎么走？

这是三个决策里**影响面最大的一个**，请谨慎。

**事实**：当前 `EMBEDDING_PROVIDER=hash`（本地 n-gram 哈希 + sha256，384 维，**无神经网络**）。
按 `skills/rag-knowledge-base-authoring` 的实测经验：
hash 嵌入下**补检索关键词行是有效的**（某项目召回从 4 次涨到 43 次），
但**微调同义措辞无效**（同义改写不提升字面重合），且排序带噪声（带符号分量互相抵消）。

**选项**：

- **C1**：保持 hash，**只做能提升字面重合的改动**（重写逆行章节的检索词、拆区域、嵌类别代号）。
  成本低、无依赖。**但不能保证命中** —— 逆行章节的检索词行已经写得很全了，仍然 0/5。
- **C2**：换成 `openai_compatible` 接语义嵌入模型。
  这是**根本解**（同义泛化、排序质量），代价是：需要接一个嵌入服务、**重新入库全部 5 份文档**、
  重新标定 `rag_score_threshold`、重跑检索审计确认零退化。
- **C3**：先 C1 后 C2（分两步，C1 立刻做，C2 单独立项）。

**建议**：本轮的可行区间是 **C1 + C3 的第一阶段**。
理由：C2 动的是检索底座，会影响**所有**历史结论的可比性，应该单独立项而不是夹在知识库补充里做。

## 七、参考：本项目 RAG 写作规范要点

完整规范见用户级 skill `rag-knowledge-base-authoring`（**动手前必读**）。核心 6 条：

1. 禁用 Markdown 表格，一律条目式。
2. 每条规则自带业务标识（区域名），不依赖章节标题。
3. 按「类型/分类」组织的文档**必须补 `**检索关键词**：` 行**，用词与查询构造一致。
4. **原始代号与中文名同时写**（`p11（禁止鸣喇叭）`），因为查询里可能拼英文代号。
5. 绝不编造内部制度；每条标注法规全称 + 条款号。
6. 技术类对照表至少两个来源交叉验证，冲突项**显式列出分歧**而不是默默选一个。

**本次新增的两条（原 skill 未覆盖，已回写 skill）**：

- **概念不在模型输出类别集合里 = 结构性不可召回。**
  如果某类知识对应的概念**根本不会出现在查询词里**（模型产不出那个词），
  那么无论文档怎么写检索词都命中不了。此时唯一出路是**把该概念挂到能产出的词上**
  （如「逆行」挂到 `car`/`pne`/`校园主干道`），或改走语义嵌入。
- **通用词堆叠块会霸榜。** 一块里塞满「交通安全、消防安全、食品安全」这类跨主题通用词，
  会对**所有**查询拿高分，挤掉真正相关的块。写文档时要控制通用词的密度，
  避免出现「什么都沾一点」的综述型长块。

## 附：本次诊断的可复现脚本（已跑完删除，需要时重建）

```python
# 针对「隐患类型」的召回探针 —— 与 verify_knowledge_recall.py 互补
import json, sys, urllib.request
sys.stdout.reconfigure(encoding="utf-8")

QUERIES = [
    "校园主干道 图书馆北侧 pne car 校园交通安全巡检",
    "停车场 地下车库 pn car 校园交通安全巡检",
    "校门口 东门 i5 motorcycle car 校园交通安全巡检",
]
FINGERPRINTS = {
    "逆行章节": ["被动逆行", "复新地面导向箭头"],
    "违停章节": ["补划并复新车位标线", "越线、占道、跨位"],
}
for q in QUERIES:
    req = urllib.request.Request(
        "http://127.0.0.1:8000/api/v1/knowledge/search",
        data=json.dumps({"query": q, "top_k": 5}).encode("utf-8"),
        headers={"Content-Type": "application/json"},
    )
    for i, hit in enumerate(json.load(urllib.request.urlopen(req, timeout=30))["hits"], 1):
        content = " ".join(str(hit["content"]).split())
        tag = "/".join(n for n, ks in FINGERPRINTS.items() if any(k in content for k in ks)) or "-"
        print(f"{i}. {hit.get('score')} | {hit.get('document_name')} | {tag}")
```
